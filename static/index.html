Simply Hook Executor

Secure Execution Daemon

Sign in with a full-HMAC (CANONICAL_V1) API key. Both the key and its signing secret are required — this dashboard signs every request it sends.

Every request is signed with HMAC-SHA256 over METHOD + PATH_AND_QUERY + TIMESTAMP + BODY and sent as X-API-Key, X-Timestamp and X-Signature-256. Signing uses the browser's Web Crypto API over HTTPS or on localhost, and an identical built-in fallback on a plain-HTTP LAN address, where Web Crypto is not exposed at all. Third-party webhook senders that cannot sign this way authenticate against a hook's own HMAC_ONLY mode instead, keyless — this dashboard always uses a real API key.
Leave blank unless a reverse proxy rewrites the path. Signatures must cover the path the server sees: if the proxy strips a prefix (/hook_executor/api/hooks → /api/hooks), keep /api; if it forwards the prefix untouched, set /hook_executor/api. Requests themselves are always sent relative to this page.

How Hook Authentication Works

            
        

        

            

                
1. An API key is always the primary authority

                

                    Any request that carries a valid X-API-Key naming a key with
                    can_execute=true on the target hook may run it —
                    regardless of that hook's own Auth Mode setting below. A hook's
                    Auth Mode only ever adds a way in for a caller presenting no API key at
                    all; it never removes, narrows, or overrides the always-available keyed path.
                

                

                    Whether that keyed request must also carry an HMAC signature
                    (X-Timestamp + X-Signature-256) depends on the
                    key, not the hook: a key with can_manage_keys must
                    always sign, and every deployment can additionally require it of every key via
                    REQUIRE_SIGNED_REQUESTS. Otherwise, an unsigned bearer request — the
                    header alone — is enough.
                

            


            

                
2. The three ways a keyless caller can reach a hook

                

                    
Standard API Key Required CANONICAL_V1 / API_KEY_ONLY

                    

                        The default. A caller with no X-API-Key is refused outright —
                        this hook is reachable only through a real, permitted key, signed or not per
                        the rule above. The two backend values differ only in what they document
                        about a keyed caller's intent (whether it is expected to also sign a
                        custom template); a keyless caller cannot tell them apart.
                    

                    
External Webhook HMAC Signature HMAC_ONLY

                    

                        For third-party senders (GitHub, Forgejo, GitLab, …) whose signature format
                        cannot be changed. A keyless request is accepted if it carries a valid
                        HMAC-SHA256 signature over the raw request body alone, computed
                        with this hook's own secret — no API key, no timestamp, and therefore
                        no anti-replay protection: a captured request stays valid
                        forever. A caller presenting a real API key still bypasses this entirely (see
                        §1) — that key's own rules govern instead.
                    

                    
Public / No Auth Required NONE

                    

                        A keyless, completely unauthenticated request is accepted outright — but only
                        when this deployment's REQUIRE_SIGNED_REQUESTS is false.
                        A deployment that has opted into mandatory signing everywhere else refuses this
                        shape of request too, rather than leaving one open door.
                    

                

            


            

                
3. External webhook header formats

                
An HMAC_ONLY hook checks a header you configure — defaults shown:

                
X-Signature-256: sha256=<hex-encoded HMAC-SHA256 of the raw body>

                
GitHub/Forgejo-style senders use a different header name by convention — set the
                    Signature Header and Signature Prefix fields to
                    match what the sender actually transmits, for example:

                
X-Hub-Signature-256: sha256=<hex-encoded HMAC-SHA256 of the raw body>

                

                    The algorithm is always SHA-256; only the header name and the string prepended to
                    the hex digest are configurable per hook.
                

            

        

    


    
    

        

            
Lineage

            
        

        

            

                Lineage records who created a key, for cascading deletion and visibility only
                (RBAC_MODEL.md R3) — it confers no rights. A daughter of the Master key
                is an ordinary daughter key with no elevated standing.
